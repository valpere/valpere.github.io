## Огляд

Більшість прототипів на n8n чи Make.com працюють на десяти тестових записах і ламаються в перший же тиждень реального навантаження: сплеск вебхуків підвішує один процес, таймаут LLM мовчки губить оплаченого ліда, а неконтрольований цикл ретраїв за ніч спалює баланс API. Продакшн-хаб оркестрації на self-hosted n8n + LLM розгортається в Docker Queue Mode з PostgreSQL і Redis — стабільно приймає вебхуки, пропускає дані через типізовані LLM-кроки з лімітами витрат, синхронізує CRM, пошту, Google Sheets і Telegram та миттєво сповіщає про будь-який збій зовнішнього API.

**Результат: швидкість візуальних воркфлоу в поєднанні з інженерною надійністю бекенду — кожен збій ліда перехоплено й можна перезапустити, прогнозовані витрати на токени та повний контроль на власному VPS без SaaS-націнок за кожну операцію.**

---

## Справжня складна задача

Візуальні конструктори приховують класичні проблеми розподілених систем: повторна доставка вебхука створює дублікати угод у CRM, ліміти частоти LLM обривають сценарій на півдорозі, а ручні правки у вебінтерфейсі не залишають історії змін. Справжня інженерна задача — обгорнути візуальний сценарій у продакшн-дисципліну: черги воркерів на Redis, перевірку ідемпотентності, сувору валідацію JSON-виходу моделі, алертинг помилок із повторним запуском (replay) та бекап сценаріїв у Git.

---

## Як це працює

1. **Прийом вебхуків і дедуплікація.** Події з CRM, пошти, Telegram, форм сайту чи розкладу проходять через Nginx із TLS та перевірку ідемпотентності (`event_id` / хеш запиту в Redis/PostgreSQL), тому повторні вебхуки не створюють дублів.
2. **Паралельне виконання у Queue Mode.** Головний процес n8n лише приймає тригери та ставить задачі в чергу Redis; окремі контейнери-воркери виконують важкі LLM- та API-вузли паралельно без блокування вхідних запитів.
3. **Структуровані LLM-кроки та guardrails.** Кожен виклик моделі має сувору JSON-схему відповіді, ліміт токенів і резервну маршрутизацію провайдерів (OpenRouter, OpenAI, Claude, DeepSeek) із детермінованою перевіркою полів перед записом у CRM.
4. **Обробка помилок і повторний запуск.** Будь-який збій вузла запускає окремий Error Workflow: сирі дані зберігаються в PostgreSQL, у Telegram приходить короткий алерт із посиланням на виконання, а після відновлення зовнішнього API задачу можна безпечно перезапустити.

## Ключові рішення

| Рішення | Чому |
|---|---|
| Self-hosted Docker + Queue Mode (Redis + PostgreSQL) | Відокремлює прийом вебхуків від повільних LLM-запитів, усуває блокування SQLite і прибирає оплату SaaS-автоматизації за кожну операцію. |
| Ключі ідемпотентності перед кожним записом | Зовнішні CRM і месенджери повторюють вебхуки при таймаутах; перевірка ключа повністю виключає дублікати угод, рахунків і повідомлень. |
| Суворий JSON Schema + ліміти токенів у LLM-вузлах | Не дає «поламаній» відповіді моделі зіпсувати поля в CRM/таблицях і захищає API-баланс від нескінченних циклів. |
| Окремий Error Workflow + автобекап у Git | Тихі збої вбивають довіру до автоматизації; кожна помилка одразу видима в Telegram, а версії воркфлоу зберігаються в репозиторії. |

---

## Що ви отримуєте

- Розгорнутий і захищений self-hosted стек n8n на вашому VPS (Docker Compose, Nginx + SSL, PostgreSQL, Redis Queue Mode, щоденні бекапи)
- Робочі AI-воркфлоу, інтегровані з вашою CRM, поштою, Telegram, Google Sheets/Drive або власним REST API
- Типізовані LLM-кроки з JSON-валідацією, резервними моделями та лімітами витрат
- Систему алертингу помилок у Telegram, автоекспорт сценаріїв у Git і зрозумілу інструкцію супроводу для команди

---

## Межі

- Масовий парсинг за агресивним антиботом або потокова обробка в реальному часі (менше 1 секунди) виносяться в окремий мікросервіс на Go, який викликається з n8n, а не будуються циклами у візуальному редакторі.
- Для розгортання потрібен Linux VPS (зазвичай 2–4 vCPU, 4–8 ГБ RAM) та API-ключі цільових сервісів і LLM-провайдерів.
